[BUGS]
+ `for` loop reuses one Scope object across all iterations (mutates `it`/`at` in place rather than allocating fresh each time, unlike `interp_each_loop`'s `.each`/`.map`-style path) -- so a closure built inside a `for` loop body captures that shared, mutating scope and sees the final iteration's value once called later, not its own. Repro: `stmts := [], for [1,2,3]; stmts.push(\`it\`); end, for stmts; @puts it(); end` prints `3, 3, 3` instead of `1, 2, 3`. Same bug class as `var` in a pre-`let` JS loop. Found via temp/scope_visibility_brainstorm.txt.
+ String literals interpret to a raw Ruby `::String`, not a wrapped `Ore::String` — so per-literal metadata (e.g. `quotation_style`, added for Member/Struct display) only survives when a value is used directly at the same call site; it's gone the moment the string passes through a variable first. Want to make string literals interpret to a real `Ore::String` instance generally. Bigger than it sounds: touches every place that currently assumes a raw Ruby string (native string methods, `.is_a?(::String)` checks, Ruby proxy methods). (The raw-string-on-the-left `==` asymmetry this used to also list is fixed now — `Ore::String#to_str` closes it, see Done.)
+ `src/compiler/parser.rb`: `begin_expression`'s bare-comma branch (`eat and nil`) isn't dead/mistake-only code -- tried raising there and it broke `Tuple { values, ... }` in `preload.ore` itself. The nil-init idiom (`ident,`) only parses the identifier, not its trailing comma (`parse_nil_init_expr` never eats it), so the *next* loop iteration of whatever's collecting body/list expressions (`parse_type_decl`'s member loop, at least) lands on that leftover comma and relies on this branch to silently swallow it. A real fix needs to tell "leftover separator from a nil-init decl" apart from "genuinely stray/doubled comma" -- not obvious how to do that from `begin_expression` alone, since by then the caller's context (what loop we're inside, whether the prior expression was nil-init) isn't visible. Punting on "make bare comma-sequences imply a Tuple" entirely too -- top-level `a, b` already means two statements throughout the language (`funk(true), funk(false)` in test/regression_test.rb), so that'd be a breaking semantic change, not a bug fix.
+ Bare Type stringification is unreliable: `Number.to_s()` "works" by accident (a Ruby proxy quirk echoes the type's own name back), but Ore-level `to_s{;}` (String, Array, ...) reads an instance member that's still `nil` on a bare, never-constructed Type -- prints empty. Found via `<String, Number>.to_s()` showing `<, Number>`. No real "what should a bare Type print as" mechanism exists yet.
+ Parser hangs forever (infinite loop, not an error) on `foo(X < Y)` -- a capitalized-identifier comparison used as a call argument. Confirmed pre-existing on `main`, unrelated to the `TYPE_IDENTIFIER '<'` dispatch fix above (same hang with and without it) -- something in `parse_circumfix_expr`'s argument loop specifically, not the top-level statement case that fix covers. Not chased down; do not add as a test without a way to bound it (would freeze the whole suite).
